# Update — 2026-11-03

A YNAB-style personal budgeting app, used as a learning vehicle for disciplined
AI-assisted development. Public GitHub repo, Go backend. Today was all **foundations,
product spec, and process** — no feature code yet. MVP build starts next.

## What got done today

- **12 pull requests, all merged.** Everything went through feature branches → PR →
  merge; `main` is protected and was never touched directly.
- Established the **engineering guardrails**, wrote and iterated the **product spec**,
  and codified a **feature workflow** to follow from here on.

## Where things stand (all on `main`)

**Engineering setup / guardrails**

- **Branch protection on `main`:** strict GitHub ruleset, *no bypass for anyone* (PR
  required, no force-push/deletion) — verified by a real rejected push. Works because
  the repo is **public** on the Free plan (going private silently disables it — a
  constraint we hit and reverted).
- **Local git hooks:** `pre-push` blocks direct pushes to `main`; `pre-commit` scans
  for secrets.
- **Secrets locked down:** `.gitignore` + a `.claude/settings.json` that denies agents
  reading `.env*` / `secrets/**`.
- **Operating rules** in `AGENTS.md` (feature-branch only, PR-only merges, test-first,
  no committed secrets, manual-only destructive prod changes); `CLAUDE.md` imports them.
- **Backend:** Go 1.27, standard-library `net/http`, one `/health` endpoint, written
  test-first. `scripts/dev.sh` (run locally) and `scripts/test.sh` (unit/integration/e2e).

**Product spec (`docs/specs.md`)** — a flow-first, YNAB-like model told as user journeys:

- The core loop: **add account → money lands in Ready to Assign → assign every dollar →
  spend → balances roll forward.**
- The governing rule: **accounts total = Ready to Assign + sum of category Available.**
- Month-end overspending/rollover (cash overspend is deducted from next month's Ready to
  Assign).
- A worked numeric example ($3,000 income, one overspend, rollover) that doubles as test
  cases.
- Decisions locked: **$0 transactions rejected; Refund is a first-class action; two
  inflow types (starting balance vs income); editing/deleting deferred but roll-ups
  designed to be edit-safe.**
- An explicit **roadmap** of out-of-scope items (credit cards, loans, recurring
  transactions, reconciliation, reports, bank sync) — MVP is **cash-only**.

**Process (`docs/feature-workflow.md`, now binding via `AGENTS.md`)** — every feature
follows: **interview-first** (questions one at a time, options + recommendation, cite
YNAB help or flag "from memory", bounded web research) → **Plan Mode before code** →
**functional + contract tests** with the invariant checked after every step → **clean
ports-and-adapters architecture** (rules in a core that imports no HTTP/SQL, in-memory
storage first then SQL, **numbers derived not stored, whole cents, months from day one**)
→ **test-first build** → per-feature doc → log open items.

**Trackers:** `docs/open-items.md` (7 open questions/ideas/assumptions) and
`docs/decisions/001` (an ADR weighing pairing vs PR review for agent-written code).

## Honest caveats

- YNAB mechanics were **verified against YNAB's help site via search snippets only** —
  the support pages are JavaScript-rendered and the fetch tool couldn't read their full
  text. I (the YNAB user) will confirm the non-core rules from experience.
- **Lesson learned:** stacked PRs caused merged work to strand on an intermediate branch
  (recovered via a fresh PR). Avoid stacking — sequence instead.
